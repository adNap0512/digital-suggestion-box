# AI活用開発の知見

デジタル目安箱の開発で実践したAIの使い方と、そこから確認できたことを、グループ会の共有用にまとめた資料です。詳細な経緯は `GOAL.md`、`progress.md`、`Report.md` に残しています。

## 1. 目的

開発の目的と範囲の決め方、設計の守り方、修正前の調査、環境操作、品質確認で、AIをどう使い、どこは人が判断したかを共有する。

## 2. 開発工程ごとのAI活用と知見

### ① アイデア出し・要件定義

- `GOAL.md` に、開発の目的、やること、やらないこと、完了条件を書いた。
- Goal A（保存の窓口）、Goal B（ブラウザ内への保存）、Goal C（Supabaseへの保存）に分けて進めた。
- AIが範囲を広げないよう、制約と停止条件を先に置いた。

**知見：** 最初から全部を作らせず、Goalを小さく分けると、AIに任せる範囲を管理しやすい。

### ② 設計

- Repository（保存の窓口）で、画面とデータ保存を分離した。
- 画面からデータベースへ直接つながない、という依存の方向を Rules に書いた。
- 見た目は `DESIGN.md`、画面の行き来は `docs/SCREEN_FLOW.md` に分けた。

**知見：** 守る設計を文章にしておくと、機能追加のときも既存の境界を崩しにくい。

### ③ 実装

- 開発には Cursor を使った。
- Rules と Skills で、作業時のルールと手順を定義した。
- ループエンジニアリングでは、Goal と `progress.md` を見て1周ずつ進めた。1周の中に、テスト、実装、ビルド、進捗の更新を含めた。
- 共通PFの仕様が無い週は、推測で接続コードを書かず停止している。

**知見：** 毎回細かい手順を指示するだけでなく、Goal、制約、完了条件、停止条件を渡す方法も有効だった。コミットのすべてをこのループが書いた、とまでは記録から断定しない。

### ④ 修正

- 直す前に、既存コードと Git の履歴を調べた。
- グループ会の指摘4件を調べた時点で、一覧の切り替えは修正済みコミット `f09d4d0` に入っていた。匿名・記名の任意入力と、画面遷移図の分離も対応済みだった。
- 新しく実装したのは、投稿詳細の表示位置だけである。改善案を比べてから、選んだカードの近くに出す形にした。

**知見：** 指摘をそのまま実装させず、原因と現状を先に見ると、不要な修正と影響範囲の拡大を防げる。

### ⑤ 環境操作・整備

- GitHub、Supabase、Cloudflare Workers を使った。
- 環境、SQL、デプロイ失敗の調査に AI を使った。
- SQLの本番適用、管理者の登録、APIトークンの発行、GitHub Secrets の登録は人が行った。
- 初回の配信は、テストとビルドの成功後に `Authentication error [code: 10000]` で失敗した。ログで認証エラーと切り分け、APIトークンを再発行して Secret を更新し、再実行で復旧した。コードの修正ではない。既存トークンが使えなくなった理由は、期限切れとは断定できていない。

**知見：** 調査には AI を使える。認証情報の発行や、外部サービスの確定操作は人が行う。

### ⑥ コードの品質担保

- テストの作成と実行を、開発の手順に含めた。
- Repository ごとのテストと、画面操作のテストがある。
- 2026-11-19 の自動テストは、23ファイル・128件が成功した。テストは本番の Supabase へはつながらない。
- そのあと、ビルド、デプロイ、担当者による公開画面の確認を別々に行った。配信の1回目は、テストとビルドが成功しても失敗した。

**知見：** AIが書いたコードは、自動テストだけで完了にしない。ビルド、デプロイ、実画面の確認は別の関門にする。

### ⑦ AI活用における課題

- Rules や Skills を整えること自体に手間がかかる。
- 文書が増えると、古い記述が残る。発表記録には「認証未実装」「テスト81件」が残り、最新の状態と食い違った。
- AIの調査や提案は、必ず正しいとは限らない。一覧不具合の原因は、当初の「描画タイミング」ではなく、URLの条件が戻らないことだった。
- 外部サービスの設定、権限、仕様の採否は、人が確認する場面が残る。

### ⑧ 今後のAI活用に対するスタンス

ここは、今回の経験を一般論に広げる前の、議論用の考え方です。

新しい手法を試す価値はある。一方で、導入と維持のコストも見る必要がある。

ループエンジニアリングのような進め方も、全部を独自に整え続けるのか、公式の機能で足りるのかを含めて検討したい。

プロジェクトの規模と目的に合わせて、手法を選ぶのがよいと考えている。

## 3. 今回の開発で特に得られた知見

| 知見 | 今回の具体例 |
|---|---|
| 作業範囲と終了条件を先に渡す | `GOAL.md` と、1周ずつのループ |
| 守る設計を文章にする | Rules に書いた Repository の依存方向 |
| 修正前に現状を調べる | 指摘4件のうち3件は、調査時点で対応済みだった |
| AIと人の役割を分ける | SQL適用、管理者登録、APIトークン発行は人が実施 |
| 品質確認を段階に分ける | テストとビルドの成功後に、配信だけが失敗した |

## 4. まとめ

AIは、コードを書くだけでなく、範囲の整理、設計の維持、調査、環境の切り分け、テストの作成にも使えた。

そのまま任せるのではなく、人が目的、制約、判断基準を渡し、結果を段階ごとに確認することが必要だった。

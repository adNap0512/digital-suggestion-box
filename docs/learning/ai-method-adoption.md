# AI 開発手法の導入判断

新しい手法を次々に足さないための基準。ワークフロー自体はここでは変更しない。

実績と推測は分けて書く。速度や工数の実測値はこのリポジトリに無い。

---

## 1. 現在利用している手法

| 手法 | 置き場 | 目的 |
|------|--------|------|
| Loop Engineering | `GOAL.md` / `progress.md` / `.claude/skills/loop-engineering` | 1 起動 = 1 周。Goal と STOP で実装を発散させない |
| Cursor Rules | `.cursor/rules/` | 依存方向・デザイン・テスト・backend 許可を常時守る |
| Skills | `.claude/skills/` | 計画 / TDD / レビュー / デザインモックなど、作業単位の手順 |
| 旧 Commands | `.claude/commands/` | 学習用。現行は Skills を優先 |
| Cursor Hooks サンプル | `.cursor/hooks/` | 理解用。本番では無効 |
| Vitest + カバレッジ閾値 | `vite.config.ts` / `test-rule.mdc` | 主要画面の回帰と 80% 下限 |

## 2. 確認できた効果（記録ベース）

推測ではない、リポジトリ上の記録から言えること。

- Goal A / B / C を Iteration 付きで完了し、`progress.md` に残している
- Secret 未入力・プロジェクト未 link・仕様未確定のときに STOP し、推測実装を止めた記録がある
- 画面・Repository のテストが rules に固定され、`npm test` / `npm run build` がループのゲートになっている
- 今回のグループ会対応でも、調査 → 方針承認 → テスト先行 → 実装の順で、Repository 契約と Goal D 接続には手を出していない

「何倍速くなった」などの数値は無いので書かない。

---

## 3. 現時点で評価できないこと

- 手法導入前後のリードタイム比較
- 学習コストと維持コストの定量
- グループ会以外の現場での再現性
- Skills の自動起動を増やした場合の誤作動率

---

## 4. 新しい手法を導入する判断基準

次を**すべて**満たすときだけ検討する。

1. 既存の Goal / Rules / Skills / テストでは埋まらない、具体的なギャップがある
2. 目的が「新しいから」ではなく、品質・安全（STOP）・再現性のいずれかである
3. 学習・維持のコストが見合う説明ができる（数値は無くても、置き換える対象は言える）
4. 既存の依存方向・TDD・1 起動 1 周と矛盾しない
5. 同時に複数導入しない。効果は `progress.md` かテスト結果で後から確認できる
6. 合わなければ外せる（必須化しない）

満たさない場合は導入しない。既存の Rules / Skills の更新で足りるなら、手法追加より文書修正を優先する。

---

## 5. 今後の改善方針

- まず今ある Goal / progress / Skills を運用する
- 効果が記録できない手法は定着させない
- 共通 PF 接続（Goal D）は仕様が揃ってから。手法追加で代替しない
- グループ会フィードバックのような UI 改善は、Loop の Goal 変更が不要なら通常の TDD で進める
